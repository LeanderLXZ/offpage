## 背景 / 触发

phase 2 新形态（2+2N lane，决策 #59）首次 runtime 验证跑通后，抽查
`target_baseline` 产物发现：两个目标角色的 targets 都**正好触顶 15**，
而候选池共 30 人、每人有 20+ 个够格的交互对象。

用 phase 0 摘要反查同场章数，确认被裁掉的不是噪声而是真实交互对象：

- Character B 被裁：`Character D` 42 章同场（前八世多次一剑刺死Character B、Character B接过它并
  注入灵力）、`Character J` 28 章、`Character G` 26 章、`Character F` 25 章
- Character A 被裁：`Character K` 42 章、`Character E` 29 章、`Character I` 15 章

同时验证这**不是 lane 拆分引入的**：旧形态（单次组合 call，commit
`9ca104f`）同样把 `Character D` 排除在Character B baseline 之外，两种拓扑结论一致 ——
根因是容量上限，不是 call 拓扑。（附带结论：新旧两份Character B baseline 15 条
里 14 条相同，lane 拆分无质量退化。）

按决策 #13，phase 3 stage_snapshot 三结构 keys 与 baseline 双向相等 ——
被裁的角色在全部 49 个 stage 里都不允许出现，是建模能力的实质损失，且
phase 3 起跑后再改 baseline 需重抽全部 stage。当前正处 phase 2 已完成 /
phase 3 未起跑的无痛窗口。

## 结论与决策

`schemas/character/targets_cap.schema.json` `maxItems` **15 → 20**。

选 20 而非 25 的依据是同场章数的断层：20 恰好装下所有 ≥15 章同场的角色
（含上列全部被误裁项），把 ≤12 章同场的路人长尾挡在外面 —— 后者正是决策
#54 准入门槛想砍掉的噪声。

成本实测（基于 2026-05 那次 phase 3 真实 stage_snapshot 量化）：一份
snapshot ≈ 32k 字符，三个 target 结构占 27%；每条 target 填充态 ≈ 1100
字符，从未登场态按 D4 三态规则只写空 entry（≈150-200 字符）。+5 个 target
→ 每份 snapshot 约 +3k 字符（+10%），phase 3 全程输出侧 +15 万字符量级，
运行时 Tier 0 常驻加载每角色 +1.5-3k token。数量级不变。

**决策 #27b（bounds-only-in-schema）验证**：全仓无第二处复述该数值，
所有 doc 引用都指向 schema 文件本身 —— 单点改动，三个下游结构
（`target_baseline.targets` + stage_snapshot 三结构）经 `$ref` 自动跟随。
